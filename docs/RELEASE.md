# 릴리스하는 법

`v`로 시작하는 태그를 GitHub에 올리면 나머지는 저절로 돼요. 맥·윈도우 앱을 만들고 시험해서 릴리스에 올리고, 이미 설치된 앱에 업데이트를 알려요.

## 지금 바로: v0.1.7

버전은 이미 0.1.7로 올려 두었고, 맥·윈도우 빌드와 서버 시험(윈도우·맥·리눅스)을 모두 통과했어요. 터미널에서:

```bash
cd meeting-scribe
git checkout main && git pull
git tag -a v0.1.7 -m "회의 노트 v0.1.7"
git push origin v0.1.7
```

## 다음 버전부터 (예: v0.1.8)

1. **바뀐 점 적기**: `CHANGELOG.md` 맨 위에 `## v0.1.8`을 만들고 쓰는 사람 말로 짧게 적어요.
   이 줄이 그대로 **앱의 업데이트 창**과 **릴리스 노트**에 나와요. 적지 않으면 지난 태그부터의 커밋 제목이 대신 들어가요.
2. **버전 올리기**: 세 곳의 버전을 똑같이 바꿔요.
   - `launcher/src-tauri/tauri.conf.json`: `"version": "0.1.8"`
   - `launcher/package.json`: `"version": "0.1.8"`
   - `launcher/src-tauri/Cargo.toml`: `version = "0.1.8"`
3. **main에 올리기**: 커밋하고 `git push`.
   GitHub의 Actions 탭에서 "맥 앱"·"윈도우 앱"·"서버 시험"이 모두 초록색인지 확인해요 (15~25분).
4. **태그 올리기**:
   ```bash
   git tag -a v0.1.8 -m "회의 노트 v0.1.8"
   git push origin v0.1.8
   ```

## 태그를 올리면 일어나는 일

- Actions의 **"릴리스"**가 맥(.dmg)과 윈도우(.exe)를 새로 만들어 시험해요 (20~30분).
- [Releases](https://github.com/jhkim0602/meeting-scribe/releases)에 새 릴리스가 생겨요.
  - 설치 파일: `MeetingScribe_버전_mac-arm64.dmg`, `MeetingScribe_버전_windows-x64-setup.exe`
  - 자동 업데이트용: `.app.tar.gz`, `.sig`, `latest.json` (사용자가 받을 필요 없음)
- 이미 설치된 앱(v0.1.2 이상)은 켤 때 새 버전을 확인해요. 새 버전이 있으면 바뀐 점과 **[나중에] / [지금 업데이트]** 창을 띄워요.

## 하지 말 것

- **웹에서 릴리스를 먼저 만들지 마세요** (Releases → Draft a new release). 그러면 `CHANGELOG.md`의 바뀐 점과 업데이트 파일이 제대로 붙지 않을 수 있어요. 태그만 올리면 돼요.
- **같은 태그를 다시 쓰지 마세요.** 잘못 올렸으면 버전을 하나 올려 새 태그로 내요.
- **세 곳의 버전이 다르면 안 돼요.** 앱이 자기 버전을 잘못 알아 업데이트를 계속 알리거나 알리지 않아요.

## 잘 안 될 때

- **Actions가 빨간색**: 실패한 단계를 눌러 로그를 봐요. 빌드나 시험이 실패하면 릴리스는 만들어지지 않아요. 고쳐서 main에 올린 뒤 **새 버전 번호로** 다시 태그를 올려요.
- **업데이트 알림이 안 떠요**: 앱이 켜진 뒤 10초쯤 기다리거나, 메뉴 막대(윈도우: 작업 표시줄 오른쪽 아래) 아이콘 → **업데이트 확인**을 눌러요. v0.1.1 이하에는 자동 업데이트가 없어서 새 .dmg·.exe를 직접 받아 설치해야 해요.
- **서명 키**: 자동 업데이트 파일은 저장소 Settings → Secrets의 `TAURI_SIGNING_PRIVATE_KEY`로 서명해요. 이 키를 바꾸거나 지우면 설치된 앱이 업데이트를 받지 못해요.
